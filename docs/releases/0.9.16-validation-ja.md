# Ooki Grader 0.9.16 検証記録

## モデル選択と上限への対応

- 既定の接続は `gemini-3.8-flash`。ひな形抽出・初回採点・再確認を優先する。
- 氏名だけを読み取る処理は `gemini-3.5-flash-lite`。初回採点と同時に氏名も読み取る場合は、採点と同じ3.8のリクエストに含める。
- 3.8のHTTP 429に限り、同じ問題・画像・リクエストキー・出力スキーマを3.5に送る。3.5も失敗した場合は既存の再試行処理へ戻し、内部で循環させない。
- 日次上限はGoogleのQuotaFailureの `PerDay` を確認し、太平洋時間の次の午前0時まで待機する。その他の上限はRetryInfo／Retry-Afterを使用し、待機時間がない場合は60秒とする。
- 待機期限をデータフォルダーに原子的に保存する。APIキーのSHA-256と期限のみを使い、キーを保存しない。再起動後も待機を引き継ぎ、期限後は3.8へ戻る。同じキーの並行処理は上限応答を共有する。
- 利用履歴のRequestedModelは設定上の優先モデル、ActualModelは実際のモデル。3.5の価格が登録されていればその価格を使い、なければ予約した見積額を保持する。3.8の価格を3.5のトークン数に適用しない。
- 認証・設定・安全性・通信結果不明・HTTP 503は上限扱いにしない。既に受け付けられた処理を重複送信しない。

## ページのまとめ処理

採点は同じ生徒の画像を既存の容量制限内でまとめる。1チャンクは最大32画像・12 MiBで、問題一覧とともに送る。上限時にもページを捨てず、そのまま3.5へ渡す。他の生徒の答案と混ぜない。

現在の既定プロファイルは同期APIをキューから実行する `queued_standard` / `expedite_standard`。Googleの非同期Batch APIとは異なる。既存の非同期バッチの監視・結果回収は変更していない。その別枠の上限に対するモデル切り替えは、この同期APIの切り替えの対象ではない。

Googleの上限はプロジェクト／モデルの利用枠であり、全利用者に一律20回というカウンターは設けていない。同一プロジェクトの別APIキーからの利用もGoogle側の429で検出する。

## 確認結果

- オフライン全体試験：.NET 1,129件成功、10件は外部環境が必要なためスキップ。フロントエンド185件成功。
- 重要処理の3.8選択、氏名の3.5選択、429時の内容不変、並行8件での一次上限応答共有、再起動後の待機、解除後の復帰、キー交換、他モデルの不変更、日次リセット、非429時の不再送を検証。
- 実API試験：3.8の429をHTTP層で再現し、その後の3.5への送信だけを実APIで行った。架空生徒の3問（東京／東南アジア諸国連合／ヒンドゥー教）が正しく読み取られ、8点／10点／8点の提案を確認した。Googleの実際の利用枠を故意に使い切る試験ではない。
- 費用精算を含む最終の関連試験193件が成功。実際の採点ワーカーで、切り替えたモデルと利用履歴、価格スナップショット、予算精算を確認した。3.5の価格の有無を両方試した。
- School Managerの自動配信・名簿照合・送信結果不明時の保護は既存試験を再実行。実際の保護者への送信は実施していない。
- Windows x64の配布用EXEを独立データフォルダーで起動し、旧版で作った架空の名簿・答案・確定結果・原本PDF・結果PDF・School Manager設定を照合した。保持に関する10項目が成功。APIキーの暗号化ファイル、フィンガープリント、参照先、リビジョンも一致し、起動時の両モデル接続確認が成功した。再起動で更新処理が繰り返されないことも確認した。

## 残る実環境の制約

2026年10月2日、提供された理科PDFを3.8へ直接送った試験は `gemini_provider_unavailable`（HTTP 503）で失敗した。PDFの各ページを画像化した診断でも同じ応答になった。3.8で62問の抽出が完了したという結果は得られていない。これを429扱いにして自動でモデルを変えることはしていない。

0.9.16は確認版として公開する。上限時の切り替えと実APIでの3.5採点は検証済みだが、提供PDFでの3.8生成とSchool Managerでの実送信・受信を完了した正式版とは扱わない。
